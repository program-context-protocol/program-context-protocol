# Getting Started

This is the operational companion to `README.md`. README explains what PCP is
and why; this file exists so a first run — human or agent — doesn't have to
rediscover the following the hard way.

## Prerequisites

- `git` on `PATH` — required.
- `claude` CLI on `PATH` — required. PCP's build/kickoff/pm/gate commands
  drive it directly; nothing in PCP talks to an LLM API on its own.
- `opa` (Open Policy Agent) — **optional**, but several checks quietly
  degrade without it: escalation routing (`escalation.rego`), bypass-reason
  rejection (`bypass_approval.rego`), and coupling-threshold color bands
  (`coupling_threshold.rego`) all fall back to conservative hardcoded
  defaults when `opa` isn't on `PATH`, rather than failing. Install it
  (https://www.openpolicyagent.org/docs/latest/#running-opa) if you want
  those policies actually evaluated instead of defaulted.
- `python3` (3.10+).

Run `pcp doctor` after install — it reports exactly which of the above (plus
optional extras: `gh`, a test runner, lint, SAST, coverage, Playwright,
Context7) it found, rather than you guessing from a stack trace later.

## First run

```
pip install program-context-protocol
cd your-project
pcp init
pcp doctor
```

`pcp init` scaffolds `.pcp/` and installs a commit-msg + post-commit git
hook. It does not touch `.claude/settings.json` — it writes
`.pcp/RECOMMENDED_PERMISSIONS.md` instead, which you review and merge
yourself.

To work on PCP itself instead of using it as a dependency:

```
git clone https://github.com/program-context-protocol/program-context-protocol
cd program-context-protocol
pip install -e .
python3 -m pytest tests/ -q
```

If you're doing this on a fresh clone with `opa` installed, expect the full
suite to pass clean. If a handful of tests skip with "not installed" (e.g.
`falsegreen`, `cosmic-ray`), that's an optional-tool gap, not a real failure
— `pcp doctor` will tell you which optional tools it detected.

## What gets tracked vs. not, for *your* project

`pcp init`'s own `.gitignore` scaffold keeps `.pcp/`'s **governance** files
tracked in git deliberately — `objective.md`, `target_state.md`,
`architecture.md`, `ci_rules.yaml`, `controls.yaml`, module specs — those
are the spec-as-truth PCP is built around, and are meant to be reviewed in
PRs like any other source file. Only the **run-time operational writes**
(`telemetry.jsonl`, `decision_log.jsonl`, `token_ledger.yaml`,
`build_progress.yaml`, evidence/transcripts) are gitignored by default, on
the same logic as ignoring `*.log` — they're regenerated by running the
tool, not authored.

This repo (PCP's own) is a deliberate exception, not the template: because
it dogfoods itself, its own `.pcp/`, `CLAUDE.md`, and `docs/CHANGELOG.md`
are gitignored entirely as project-specific internal state — see
`.gitignore` here. If you `git clone` this repo itself expecting to see its
own audit trail, you won't; that evidence only ever existed on the
maintainer's machine. Your own project, scaffolded fresh by `pcp init`,
behaves as described in the paragraph above instead.

## Unattended / `--yes` mode — know the trust boundary before you use it

`pcp build --yes` and `pcp deploy --yes` skip the interactive confirmation
step, for CI or cron use. Both can reach a `subprocess.run(..., shell=True)`
call — `pcp build`'s install-only fast path, and `pcp deploy`'s
trigger/rollback step — executing a command string that comes from
`.pcp/integrations.yaml` or a build candidate's own declared install
command. That's fine when you configured `integrations.yaml` yourself and
trust every module spec in the repo; it is not a sandbox, and nothing
allowlists the command string. Don't run `--yes` in a context where either
of those inputs could come from someone you don't trust.

## When something fails

In rough order of where to look:

1. `pcp doctor --check` — environment/config problems.
2. `.pcp/build_report.md` (after a run) — per-criterion evidence summary.
3. `pcp build-status` — live view of an in-progress run.
4. `.pcp/escalations.yaml` / `pcp escalations` — anything that got flagged
   for a human and is still open (`ack` ≠ `resolve` — acknowledging isn't
   the same as fixing it).
5. `pcp telemetry` — per-module attempt/cost/conflict-rate rollup, including
   a `result: skipped` vs `result: error` vs `result: bypassed` breakdown
   per control — a check that never ran looks different from one that
   passed, on purpose.
6. `pcp provenance` — full per-file × control audit trail if you need to go
   deeper than the telemetry rollup.

## What this file is not

Not a CLI reference — `pcp --help` and `pcp doctor` are the live source of
truth for that, per README. This file only covers the parts a first run
tends to trip over that aren't obvious from `--help` output alone.
